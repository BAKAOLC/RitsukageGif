# Diagnostic logging

日志默认写入 `%LOCALAPPDATA%\RitsukageGif\logs`。设置了 `RITSUKAGE_DATA_DIRECTORY` 时，使用该目录下的 `logs` 文件夹。

桌面程序、命令行客户端和语言服务器按进程与会话分别写文件：

```text
rg-<pid>-<session>-<role>-<date>-<sequence>.log
```

日志正文、事件名和字段使用英文。系统异常可能保留系统提供的语言。语言服务器的标准输出只用于协议，日志不会混入协议内容。

## 内容

记录启动与退出、命令和全局动作、设置保存、选区、采集与编码、导出、编辑、贴图、识别、脚本和更新检查。失败保留异常消息、堆栈和内部异常；已知脚本诊断记录类型与行列，不写脚本原文、识别文字、图像像素或外部凭证。

截图和长截图还记录窗口句柄、位置、可见性、启用状态、置顶状态及 Windows cloak 状态。查找同一操作的 `OperationId`、`SelectionId` 或 `SessionId` 可以串起各阶段。正常取消单独记录，不当成程序崩溃。

## 级别与保存

默认级别为 `Debug`。可在启动前设置 `RITSUKAGE_LOG_LEVEL` 为 `Trace`、`Debug`、`Information`、`Warning`、`Error`、`Critical` 或 `None`。

文件按日期或 8 MiB 滚动，默认清理超过 7 天的旧文件，并控制在 32 个文件、256 MiB 内；仍在写入的文件受到保护，无法删除时留待下次清理。关闭程序时等待已接受的日志写完。写入异步进行，有界队列为错误预留容量；发生过载或写入故障时计数并记录紧急诊断，不让日志写盘阻塞正常界面操作。

鼠标移动、像素处理和逐帧渲染不逐条记录。高频采集记录首帧、状态变化和低频统计，减少开销和无效内容。

## 故障定位

先按文件名中的 PID 和会话选择本次日志，检查最后一个已开始但未完成的阶段。长截图依次记录窗口创建、首次渲染、DWM 合成、旧遮罩交接、采集线程与首帧。保留整个会话的日志，避免只截取最后一行丢失前因。

强制终止或原生崩溃可能使最后少量日志未写入；此时还需结合 Windows 应用程序事件或崩溃转储。日志中没有错误不等于程序未发生故障。

## 日志入口与故障报告

在**设置 → 常规 → 诊断**中可以打开日志文件夹、导出诊断压缩包，或打开项目的问题反馈页面。压缩包包含日志和故障报告，不包含配置文件、凭据或录制内容。分享前请检查日志中的文件路径和错误详情。

日志默认保存在应用数据目录的 `RitsukageGif/logs` 中。该目录不可写时改用系统临时目录的 `RitsukageGif/logs`；设置中显示实际使用的目录。紧急日志也会随诊断压缩包导出。

程序会记录运行会话。异常退出后，独立监视进程尽可能记录退出码；下次启动显示尚未查看的故障记录。强制关闭、断电也可能产生这类提示，因此提示不会把所有异常退出都断言为崩溃。已查看的报告保留七天，最多保留 32 份；未查看的报告不自动删除。

动图编辑器使用独立进程解码导入的动画。解码失败或工作进程异常退出时，主程序显示导入失败，保留已有文档；可以重新打开其他文件。取消导入会结束对应的工作进程并清理临时帧。

点击“报告问题”只会打开 GitHub 的新问题页面，不会自动发送日志或提交问题。请填写复现步骤，检查并自行附加诊断压缩包。

故障报告中的退出码和最后操作不能代替原生调用栈。系统崩溃转储可用于进一步定位原生故障；程序不会自动更改系统转储策略，也不会在崩溃后尝试继续执行已损坏的原生状态。
